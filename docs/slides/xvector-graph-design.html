STAGE 04 · kNN ≈ O(new · log N) HNSW index · append-friendly

What is HNSW

Hierarchical Navigable Small World — an approximate nearest-neighbor index built as a stack of proximity graphs. The top layer is sparse with long-range links for big jumps; each layer down is denser; the base holds every vector. A query greedily hops toward its neighbors, descending layer by layer, so a lookup costs ~O(log N) — not a full O(N) scan. It updates automatically as rows are inserted, which is why it is the default for an append-target table.

The query & why it stays cheap

-- per new doc: bounded by the index, not the table size
SELECT TOP 5 doc_id,
       1 - COSINE_DISTANCE(embedding, :q) AS sim
FROM   vector_embeddings
WHERE  COSINE_DISTANCE(embedding, :q) <= 0.60
ORDER BY COSINE_DISTANCE(embedding, :q);

Reading the picture

  • Each dot is a document, placed by its embedding — closer dots are more similar. 64 dimensions, flattened to 2D here.
  • The ring around a dot covers its N nearest neighbors — its reach. Every dot has one; a few are drawn to keep it legible.
  • The thin links are the stored neighbor edges — this is the HNSW base layer.
  • The search starts at an entry point on the far side and walks neighbor→neighbor, each hop landing closer, until it steps onto Q's disk — it never scans every dot.

When a new document arrives

  1. Embed it → it drops in as point Q.
  2. Find which rings Q falls inside — its nearest neighbors. HNSW navigates there in ~O(log N), without testing all N rings (slide 2).
  3. Those become Q's index links and the source docs whose entities earn an EMBEDDED edge to Q's.

The closer Q sits, the smaller the distance d = 1 − cos and the larger the edge weight (1 + cos) / 2.

The ring is the intuition; HNSW is the machinery — it finds the landing neighborhood without checking all N rings.
